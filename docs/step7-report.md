## 7.6a 等 donor 原型

- 端到端 3 条全过（tests/step7/test_04_waitdonor.py，`1a7bc56` 起）：
    1. 接近时等 donor：闸门等到结果，tile 的 36 个 chunk 全部写入，tile 上服务器没跑 noise、features，rcon 最慢 < 1 秒；
    2. 主线程同步要一个正租着的 chunk：不等（放弃闸门），主线程只卡原版生成这个 chunk 的时间；
    3. donor 卡住：最多等 2 秒超时，原版照常生成，主线程不卡。
- **变异检查（11-09）**：计划 7.6a 要求"把导入故意改回 `server.execute`，同步等 chunk 那条测试要失败"。
  用 `MCD_MUTATE_WAITIMPORT=server scripts/test.sh step7 -k waitdonor` 跑（测试夹具发 `/donor waitimport server`，命令日志里确认生效）：
  **3 条全过，变异没被抓到。** 原因不是测试漏了，而是这条要求的前提已经不成立：原型第二版起，主线程同步要 chunk 时
  （`getChunk` 的 `managedBlock`）会放弃所有闸门、不建新的（`ServerChunkCacheSyncMixin`），主线程不会再等在闸门上，
  所以导入排在哪个队列都不会让主线程卡住。"导入走 chunk 缓存自己的队列"是第一版（没有放弃闸门时）为了不卡 2 秒加的，
  现在是多余但无害的保险，保留。计划里那条测试要求改成"同步要 chunk 时不等、不卡"（第 2 条已经覆盖）。
- **换成防现在的风险的变异检查（11-09，调度要求）**：加测试开关 `/donor waitsync wait`（主线程同步要 chunk 时照样建闸门、照样等），
  第 2 条测试加"同步要 chunk 期间不建闸门"的检查。`MCD_MUTATE_WAITSYNC=wait scripts/test.sh step7 -k waitdonor`：
  **第 2 条失败**（期间建了 9 个闸门，同步要 chunk 用了 1188 ms，等到 donor 的结果才返回）；不加变异 3 条全过（同一条 786 ms，
  是原版自己生成这个 chunk 的时间，2 核测试服务器上）。说明这条测试确实防住了"主线程卡在闸门上等 donor"。

读法和保留意见：
- **原版对照**（同批、同核、同航线长度）：卡住 33%、37%（均值 35%），距离 0.67、0.63。和 kexu 发布的原版 2 核鞘翅 120 秒（卡住 30～34%，距离 0.66～0.70）一致。
- **v0（2 个 donor，开关全关）**：卡住 30%、22%（均值 26%），距离 0.70、0.78。方向是 donor 有一点帮助（卡住少约 9 个百分点），但两轮差 8 个百分点，波动和差值一样大，下不了结论。
- **各开关**：deadline 18%（最好），throughput 24%，waitdonor 26%，territory 30%，hedge 31%。都只有 1 轮，在 v0 两轮的波动范围里，只有 deadline 略低于范围。
- **throughput、all 两类轮作废**：这几轮 donor 来源事件是 0（worker 没把结果交上来），同一批里 worker 被看门狗杀过一次：开 7.3 时一个 donor 同时领几个任务，
  worker 主线程等 chunk 时把下一个 tile 的生成嵌套进来跑，越嵌越深（已修，`1e6363e`，OneAtATime）。slow-throughput 同理。要用修好的提交重跑。
- **丢弃**：v0 两轮整个丢弃 79/185、140/210（43%、67%）。其中"来晚了"（区域已在服务器内存里）只有 0～15，最多的是"碰到服务器的 chunk"（56～96）：
  tile 回来时区域里已经有服务器生成并存盘的 chunk。这也是"来晚了"的一种：donor 跟不上玩家，服务器已经在 tile 边上生成过了。所以提前量（7.5）和预测（7.2）是方向。
  deadline 轮（按玩家预计到达时间排序）丢弃 100/210，没有明显少。
- **主线程导入耗时**：每轮 1.2～1.5 秒（120 秒里），约占主线程 1%，不是瓶颈。MSPT 均值两个 18 ms 的轮（原版对照第 1 轮、territory）是个别长 tick 拉高的，其余 2.5～4 ms。
- **7.5 提前量**：look16 v0 接受 217、丢弃 39（15%），卡住 26%；默认 8 圈的 v0 丢弃 43～67%；look24 丢弃 44%、卡住 34%。16 圈丢弃最少，值得在部署机器上细测。
- **7.5 tile 大小**：tile2 卡住 29%、tile8 41%（接受只有 34 个，大 tile 做得慢、跟不上）；默认 4。
- **"donor 来源事件"的口径**：飞行记录里 donor 是导入时写进存档的 chunk 数（tile 加外圈），vanilla 是服务器做完的 chunk 数——其中包括导入的半成品被服务器接着做完的，
  所以不能直接当"服务器自己生成了多少"。要知道玩家看到的 chunk 有多少来自 donor，得按 chunk 坐标把导入和玩家视野对起来，留到正式测量。

### donor 的活有多少是在玩家前面

按飞行记录（provenance.jsonl 的 donor 事件和逐秒玩家位置）算：每个 donor 写入的 chunk，写入那一刻在玩家前方多远（沿飞行方向，chunk）。

| 轮 | donor 写入的 chunk | 导入时在玩家前方 ≥ 10 个 chunk | 在玩家身后（已经飞过） | 领先量中位数（chunk） |
|---|---|---|---|---|
| 1-v0 | 2376 | 2% | 97% | -67 |
| 2-v0 | 1512 | 51% | 45% | 11 |
| 3-territory | 3312 | 0% | 99% | -38 |
| 4-deadline | 2556 | 52% | 48% | 15 |
| 5-throughput | 0 | - | - | - |
| 6-slow-v0 | 864 | 100% | 0% | 67 |
| 7-slow-throughput | 0 | - | - | - |
| 8-hedge | 2628 | 25% | 74% | -98 |
| 9-waitdonor | 2340 | 0% | 96% | -43 |
| 10-all | 0 | - | - | - |
| 12-all | 0 | - | - | - |

- 差别很大：v0 第 2 轮、deadline 约一半在前方（中位数领先 11～15 个 chunk）；v0 第 1 轮、territory、waitdonor 几乎全在玩家身后——写进存档时玩家早飞过了。
- 原因：起飞时找需求把玩家周围一大片 tile 一次放进队列，donor 按扫描顺序做，玩家飞走后还在做起点附近的。不开 deadline 时队列不按方向排、也不删；
  开了 deadline，飞过的 tile 没有将来的到达时间（due 无穷大），排在最后，但别的做完了照样派。这解释了"donor 帮不上忙"的大部分：donor 的活大量白干。
- 提议（7.2b，待调度定）：开 deadline 时，玩家已经飞过、又不在当前需求范围里的 tile 直接从队列删掉。

4 核下原版基本不卡（kexu：卡 0.5 秒，距离 0.996），donor 的价值主要在 2 核这种算力紧张的情况；这一批都是 2 核。
