# 第 6 步详细计划：原型 v0（自动找需求、多个 donor）

把第 5 步的手动放任务（`/donor enqueue`）换成自动：服务器自己看玩家在哪、找出前面还没生成的地方、按 tile 放进队列；多个 donor 同时领任务。调度仍然只用先来先服务，先求跑通。

负责人：fish（分支 `fish`）。kexu 做第 4 步（benchmark 第 2 层：飞行场景、虚空率、实时地图），第 6 步的正式验收要用它。

## 0. 先要解决的问题：相邻 tile 的接缝

第 3、5 步的测试都故意把 tile 隔开。第 6 步自动找需求，相邻的 tile 一定会出现，而且可能由不同的 donor 生成。

**问题在哪**（以 tile A、B 左右相邻为例）：

- A 的导出带着它外面一圈，这一圈里有一部分是 B 的 tile chunk。它们停在 `carvers`，里面有 A 的地物写过来的方块（树冠、矿脉）。
- B 的导出里，B 的 tile chunk 停在 `initialize_light`，带着 B 自己的地物，但**没有 A 写过来的方块**：B 的 donor 世界里，A 的地物从来没跑过。
- 按现在的冲突规则（存档里更完整的不覆盖，更不完整的被覆盖）：
    - 先导 A 再导 B：B 的 tile chunk（`initialize_light`）覆盖 A 带来的同位置半成品（`carvers`），**A 写进 B 的树冠丢了**。
    - B 带来的外圈里有 A 的 tile chunk（`carvers`，带着 B 写过来的方块），存档里已经是 A 的 `initialize_light`，跳过，**B 写进 A 的方块也丢了**。
- 结果：tile 边界上的树、矿脉被切断。第 3 步关卡测不到，因为它只导单个 tile。

**方案**（请审阅时选一个，我推荐 A，先做 A 并量出接缝的差异，不够再上 B）：

| | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| A. 同一个 donor 包一片 | 调度时把相邻的 tile 尽量派给同一个 donor（按 3×3 tile 的"块"分配）。同一个 donor 世界里，后生成的 tile 导出时已经带着先前 tile 写过来的方块，是超集。冲突规则补一条：**同一个 donor、同一个世界导出的，状态相同也覆盖**（每个导出带 donor 世界的编号）。不同 donor 之间的接缝照旧有问题，但只出现在"块"的边上 | 改动小；接缝只剩块边，比例可控 | 块边上仍会切断；一个 donor 掉线，它的块要整块重派 |
| B. 方块级合并 | donor 在外圈 chunk 刚到 `carvers`（还没被别人写）时记一份底稿，导出时带上"地物写进来的方块"（和底稿不同的那些）。服务器导入外圈 chunk 时，把这些方块合并进已有的 chunk，而不是整块覆盖或跳过 | 接缝完全正确，和 donor 怎么分配无关 | 要改导出格式和导入逻辑；合并进已到更后状态的 chunk 要处理高度图、光照；工作量大 |
| C. 只导入被完全包住的 tile chunk | DEV_PLAN 第 3 步的退路：外圈不导入，tile 边上一圈也不导入，只导入中间 2×2；其余由服务器自己生成 | 不会切断 | 每个 tile 只省下 4/16 的生成量，收益大减 |

**验收（无论选哪个）**：两个相邻 tile 分别由两个不同的 donor 生成，导入后和原版对照，**tile 边界两侧 2 个 chunk 内**的差异不高于同一轮没导入区域的差异；方案 A 再加一组"同一个 donor 生成"的对照，那组必须逐块一致（和 5.4 的"中间 2×2 逐块一致"一样）。

## 1. 要写的东西

### 1.1 找需求（coordinator）

- 每秒在主线程上扫一次：每个玩家周围"视距 + 4 圈"（视距 10 → 29×29 chunk）覆盖的 tile。
- 一个 tile 只在**完全没碰过**时才入队：tile 和外面一圈（6×6 chunk）在内存里都没有、存档里也都没有。服务器自己生成过一部分的地方（比如已经走过的边上），交给服务器自己生成，避免和服务器的半成品冲突。
- 查存档用 region 文件头（chunk 在不在），不读整块 NBT；结果按 tile 缓存，生成、导入后失效。查询放在存档读写线程上，主线程只看缓存。
- 主线程上每次扫描的耗时要 < 1 ms（用 `/bench stages` 那套计时量），超了就减少扫描频率。
- 队列加上限（256 个 tile），满了就不再加（先来先服务，玩家跑远了后面的自然过时）。
- 没有 donor 连着的时候不扫，0 个 donor 时服务器和原版一样。

### 1.2 多个 donor

- coordinator 第 5 步已经支持多个连接。按选定的接缝方案调整派任务的逻辑。
- 测试环境：compose 加第二个 worker 服务 `worker2`（同一个 profile），自己的存档目录 `test-data-worker2`，绑另一组核（40-43，节点 2，不用超线程兄弟核）。

### 1.3 统计和实时地图

- `/donor status` 加上：每个 donor 做完了几个 tile；"donor 没赶上"的 tile 数（导入时全部被判已加载或已存在）。
- 写入成功时调 kexu 第 4 步加的 `mcdonate.common.Provenance.report(cx, cz, DONOR, workerId)`。第 4 步合进 main 之前先空着（留一个调用点），合进来后接上。

## 2. 小步和验收

### 6.1 接缝方案（等审阅选定）

- [ ] 方案 A：同一个 donor 包一片，以及"同一个 donor 世界的导出状态相同也覆盖"的规则（单元测试覆盖冲突规则的每一种情况）
- [ ] 相邻 tile 的两组对照（见第 0 节的验收）

### 6.2 找需求

- [ ] 单元测试：给定玩家位置和已生成的 chunk，算出要入队的 tile，和手算的一致；碰过的 tile 不入队
- [ ] 端到端：假玩家站定，`/donor status` 里出现它周围"视距 + 4 圈"内没碰过的 tile；donor 做完后存档里都有
- [ ] 主线程扫描耗时 < 1 ms（打印到证据目录）
- [ ] 0 个 donor 时不扫描（`/bench stages` 里扫描次数为 0）

### 6.3 多个 donor

- [ ] 两个 worker 同时连着，任务分给两边，`/donor status` 里各自有完成数
- [ ] 运行中随机 kill、重启 donor：没有丢 chunk，日志里没有 ERROR（第 5 步的 kill 测试扩展到两个 worker）

### 6.4 跑起来（自己的冒烟测试，正式验收等第 4 步）

- [ ] 假玩家按固定速度直线移动 2 分钟（每 tick 传送一小段，或用第 4 步的飞行场景）：donor 生成的 chunk 在玩家到达前已经导入（`full_resumed` 占玩家沿途新加载 chunk 的比例 > 0，并记录这个比例）
- [ ] 连续跑 30 分钟：读取器扫描整个存档，没有读不出来的 chunk；随机抽 1% 的 chunk 和对照世界比，差异不高于没导入区域

### 6.5 DEV_PLAN 的正式验收（等 kexu 第 4 步）

- [ ] 0 个 donor：和第 4 步的原版基线比，没有可测出的差别
- [ ] 服务器限核、1 个鞘翅假玩家：2 个 donor 时，虚空率和服务器 CPU 都明显低于 0 个 donor（5 次结果的置信区间不重叠）
- [ ] 实时地图上能看到 donor 生成的 chunk 走在玩家前面

DEV_PLAN 写的是"2 核服务器"。我们的部署目标是 N100（4 核），测试默认按 4 核。正式验收用 2 核还是 4 核，请审阅时定（建议两个都跑，2 核是更紧的情况）。

## 4. 风险

- **接缝方案 A 不够**：块边上的切断如果明显（差异高于没导入区域），要上方案 B，工作量会大很多。6.1 先量出来再决定。
- **找需求太保守**：只要"完全没碰过"的 tile，玩家沿着已有地形边上走时，可能大部分 tile 都不符合条件。6.4 会量 donor 实际分担了多少；太少再考虑放宽（比如允许服务器只生成到 `structure_starts`、`biomes` 这种不写方块的阶段）。
- **主线程扫描开销**：多个玩家、视距大时扫描量会涨，靠缓存和限频控制。
- **测试资源**：再加一个 worker 要多 4 个核、6GB 内存，机器够用。
